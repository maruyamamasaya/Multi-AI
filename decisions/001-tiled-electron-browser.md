# 001: 既存 AI Web 画面を並べる Electron アプリとする

## 背景

本プロジェクトは「複数 AI を扱う基盤」として作成されたが、具体的な利用方法は未定義だった。想定する利用体験は、複数の AI サービスを一画面に分割表示し、それぞれの既存 Web 画面を使い分けることである。

## 問題

AI API を統合すると、API 契約、課金、機能差への対応が必要になる。一方、通常の Web アプリで外部サービスを `iframe` 表示する方法は、サービス側の埋め込み制限により動作しない可能性が高い。Chrome 拡張はタブの整理には適するが、一つの独自画面内に複数の実ページを自由に配置する用途には制約がある。

## 検討した選択肢

1. AI プロバイダーの API を共通 UI から呼び出す。
2. 通常の Web アプリに各サービスを `iframe` で埋め込む。
3. Chrome 拡張でタブとウィンドウを整理する。
4. Chromium を内包する Electron アプリで複数の Web ページを表示する。

## 採用した判断

Electron、TypeScript、React を使ったデスクトップアプリとし、外部 Web ページは `WebContentsView` で分割表示する。初期版では利用者が各ページを直接操作し、API 統合や DOM 依存の自動操作は行わない。

## 採用理由

- 各サービスの既存 Web UI、契約、会話履歴をそのまま利用できる。
- `iframe` の埋め込み制限を前提にせず、複数の独立したブラウザ画面を配置できる。
- 分割レイアウト、ズーム、セッション分離・共有などをアプリ側で制御できる。
- Web 技術を使ってデスクトップ UI を構築できる。
- 最初の価値を「複数 AI の作業机」に絞り、サービス固有実装を減らせる。

## デメリット・トレードオフ

- 複数の Chromium ページを同時実行するため、メモリ消費が大きくなる。
- 一部サービスでログインや認証が正常に動作しない可能性がある。
- Electron の更新とセキュリティ対応を継続する必要がある。
- 外部サービスの利用条件と画面変更の影響を受ける。
- `WebContentsView` は DOM 要素ではないため、UI レンダラーのレイアウトと座標を同期する必要がある。

## 将来見直す条件

- 主要 AI サービスの認証が Electron では安定して動作しない場合
- メモリ消費が実用上許容できず、休止制御でも改善できない場合
- ブラウザ側が複数実ページのタイル表示を正式に提供した場合
- 利用者の主要ニーズが画面併用ではなく、一括送信や回答比較の自動化だと判明した場合
